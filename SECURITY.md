## Что проверено и почему это не проблема

**1. Ключи и пароли.** В коде секретов нет. `ANTHROPIC_API_KEY` и `AIRL_ADMIN_TOKEN`
объявлены через `defineSecret(...)` (Google Secret Manager) в `functions/index.js` — это
правильный паттерн, значения нигде не хранятся в репозитории. Файлы новые, ещё не
закоммичены — утечки в историю git нет.

Единственный ключ, который виден в браузере — `AIzaSyDNS...` (Firebase Web API key) в
`diagnostics.html` и в атрибуте `data-key` у `airl-lead.js`. Это не секрет в обычном
смысле: он и раньше был публичным в `firebase-bridge.js` этого же проекта. Защита идёт
не через секретность ключа, а через правила Firestore (ниже) и, отдельно, через
ограничение по домену в Google Cloud Console — оно пока не проверено (см. «Что сделать
руками»).

**2. Доступ к данным.**
- Все четыре функции (`group`, `diagnostics`, `lesson1`, `closeGroup`) проверяют заголовок
  `x-airl-token` на сервере (`guard()` в `functions/index.js`), сравнивая с настоящим
  значением секрета — не сравнением на клиенте. Пароль в `admin.html` не хардкожен: форма
  реально стучится в функцию и получает 401, если пароль неверный. `sessionStorage`
  используется только чтобы не вводить пароль на каждый клик — это нормально для панели
  на 1–2 человек, не постоянная сессия.
- Правила Firestore проверены построчно после ручного слияния: старые блоки `requests` и
  `tasks` не тронуты, новые (`leads`, `groups_public`, `groups`+`responses`) добавлены
  внутрь того же `match /databases/{database}/documents`, catch-all `match /{document=**}`
  (запрет всего остального) остался последним и продолжает действовать. Скобки сбалансированы.
- `groups/{code}` целиком закрыт (`allow read, write: if false`) — только Cloud Functions
  с Admin SDK видят данные группы и ответы сотрудников. Вложенная `responses` разрешает
  `create` только если код группы существует и активен, и требует все обязательные поля
  анкеты — это тоже серверная проверка (Firestore применяет `firestore.rules` независимо
  от того, идёт запись через SDK или через голый REST, как в `diagnostics.html`).
- `groups_public/{code}` отдаёт наружу только `company` и `active` — ни один личный
  ответ сотрудника через неё не виден.
- Файлы отчётов (Excel, презентация) отдаются подписанными ссылками на 30 дней
  (`getSignedUrl`, проверено в `agents/diagnostics.js` и `agents/lesson1.js`) — правила
  Storage в этом репозитории вообще не участвуют, доступ идёт только через подпись,
  сгенерированную сервером.

**3. Вводимые данные.** Firestore-правила проверяют длину и тип полей на сервере
(`leads`, `responses`) — это не только проверка в браузере. Cloud Functions валидируют
код группы и содержимое запроса до вызова модели.

**4. Логи.** Единственный `console.error` (в `fail()`, `functions/index.js`) печатает
объект ошибки — это стандартная практика, специальных полей с паролями или токенами
в логи не выводится.

## Что сделать руками (не могу сделать сам)

### 1. Задать секреты перед деплоем функций
Зачем: без них функции не задеплоятся, а пароль/ключ никогда не должны появляться в
переписке или в коде.

```
firebase functions:secrets:set ANTHROPIC_API_KEY
firebase functions:secrets:set AIRL_ADMIN_TOKEN
```

Выполните это в своём терминале (не через меня) — так значения не попадут ни в один чат
или лог. Для `AIRL_ADMIN_TOKEN` придумайте длинную случайную строку — это единственная
защита `/admin.html`.

### 2. Ограничить Web API key по домену
Зачем: ключ публичный по природе, но без ограничения им можно достучаться до вашего
Firestore REST API с любого сайта (сами данные всё равно защищены правилами, но домен
экономит от чужого фонового шума и спама).

1. [Google Cloud Console → API Credentials](https://console.cloud.google.com/apis/credentials?project=landing-page-8e314)
2. Откройте ключ `AIzaSyDNS...` (Browser key)
3. Application restrictions → HTTP referrers → добавьте `https://airl.kz/*` и `https://www.airl.kz/*`
4. Проверка: с другого домена запрос к Firestore REST с этим ключом должен вернуть ошибку

### 3. Потолок расходов на Anthropic
Зачем: агент вызывает модель на каждое нажатие «Собрать портрет» / «Собрать урок» —
без лимита всплеск использования не остановится сам.

1. [console.anthropic.com](https://console.anthropic.com) → Settings → Limits
2. Задайте месячный лимit (README пакета оценивает один прогон агента 1 в 30–60 тыс.
   токенов на вход, до 16 тыс. на выход — ориентируйтесь на ожидаемое число групп в месяц)
3. Проверка: лимит должен отображаться в разделе Limits как активный

## Можно позже

- CORS функций (`functions/index.js`, `OPTIONS.cors`) включает `http://localhost:5173`
  вместе с `https://airl.kz` — это для локальной разработки, в бою не используется и не
  открывает ничего постороннего. Можно убрать, когда не будет нужен локальный тест.

# Обновление — чат-агент диагностики (2026-08-26)

Анкета сотрудников (`diagnostics.html`) стала живым разговором с моделью вместо формы с
полями. Это новый публичный (без пароля) эндпойнт `interview` в `functions/index.js`,
который дёргает Anthropic на каждое сообщение сотрудника — принципиально другой профиль
риска, поэтому разбираю отдельно.

## Итог: можно показывать людям — ДА, один шаг важнее, чем раньше

| Срочность | Что нашли | Кто чинит |
|---|---|---|
| 🔴 Срочно | потолок расходов на Anthropic (см. пункт 3 выше) теперь не «можно позже», а обязателен | вы, 2 минуты — сделайте перед публикацией, не после |
| ✅ Проверено | XSS в чате | защита есть, см. ниже |
| ✅ Проверено | путь-инъекция через код группы / сессию | защита есть, см. ниже |
| ✅ Проверено | открытый счёт без лимита на публичном эндпойнте | защита есть, см. ниже |
| ✅ Проверено | внедрение инструкций через сообщения сотрудника (prompt injection) | смягчено, остаточный риск описан ниже |

## Что проверено

**1. XSS.** Всё, что печатает сотрудник, и всё, что отвечает модель, вставляется в
страницу только через `element.textContent` (`diagnostics.html`, функция `addBubble`) —
никогда через `innerHTML`. Даже если сотрудник отправит `<script>` или модель вернёт
разметку в ответе, браузер покажет это как обычный текст, а не выполнит. Проверил
`grep -n innerHTML diagnostics.html` — двух мест: `wrap.innerHTML = ""` (просто очистка)
и статичная разметка индикатора «печатает» без единой подстановки данных.

**2. Инъекция через параметры запроса.** `code`, `session_id`, `department` — единственные
поля, которые попадают в путь документа Firestore (`groups/${code}/...`). Раньше формат
кода нигде не проверялся (даже в защищённых паролем функциях). Добавил
`functions/lib/limits.js`: `code` — строго `[A-Z]{1,6}[0-9]{3,6}`, `session_id` — строго
`[a-zA-Z0-9_-]{8,64}`, `department` — только одно из четырёх фиксированных значений.
Символ `/`, который мог бы увести путь в незапланированную вложенную коллекцию, запрещён
везде. Применил эту же проверку кода задним числом и к четырём старым функциям
(`group`, `diagnostics`, `lesson1`, `closeGroup`) — раньше там просто верили строке из
запроса.

Проверил тестами (`node limits_test.js`, не в репозитории — прогонял локально):
путь с `../`, слэши в коде, XSS-пейлоады в `department`, скрипт-теги в `session_id` —
всё отклоняется на входе с понятной ошибкой, ничего не долетает до Firestore.

**3. SQL-инъекция.** В проекте нет SQL-базы — только Firestore (документ-ориентированная
БД с типизированными путями, не текстовыми запросами) и Firestore REST/Admin SDK, где
запросы строятся не конкатенацией строк, а вызовами методов (`.doc()`, `.collection()`,
`.where()`) с параметрами как значениями, а не частью синтаксиса запроса — классическая
SQL-инъекция здесь неприменима по архитектуре. Ближайший релевантный риск — путь-инъекция
через `code`/`session_id` — закрыт в пункте 2.

**4. Открытый счёт на Anthropic.** `interview` — первый в проекте эндпойнт без пароля,
который платно вызывает модель. Добавил `functions/lib/sessionStore.js`: предел на
разговор (40 сообщений на сессию) и предел на день по всему проекту (400 сообщений/день)
через транзакции Firestore — жёсткий тормоз, если кто-то станет слать запросы напрямую,
в обход интерфейса. Дополнительно у `interview` в `functions/index.js` свой набор
секретов (`OPTIONS_PUBLIC`) — доступа к `AIRL_ADMIN_TOKEN` у него нет вообще, только к
`ANTHROPIC_API_KEY`: меньше секретов на самой рискованной функции.

Это снижает, но не убирает риск полностью — при желании лимиты можно обойти, создавая
много сессий. Поэтому потолок расходов в Anthropic Console (пункт выше) стал обязательным,
а не желательным шагом: лимиты в коде — это форма разговора, а не замена настоящего
потолка счёта у поставщика.

**5. Внедрение инструкций через сообщения сотрудника (prompt injection).** Системный
промпт (`functions/agents/interview.js`) явно говорит модели: сообщения сотрудника —
только источник данных для анкеты, не команды; попытки сменить роль, раскрыть промпт,
выполнить постороннюю инструкцию — вежливо игнорировать. Это снижает риск, но не
гарантирует его на 100% — так уже устроены языковые модели. Поэтому это не единственная
линия защиты: что бы модель ни решила вернуть в поле `data`, `sanitizeExtractedData()`
(`functions/lib/limits.js`) всё равно обрежет длину каждого поля, проверит типы, отбросит
незнакомые значения `frequency`, посчитает `manual_share` к ближайшему из пяти
разрешённых чисел и не даст пройти явно неполной анкете. Отдельно: направление
(HR/Finance/Marketing & Sales/CEO) модель вообще не выбирает — сотрудник называет его
кнопкой до начала разговора, сервер проверяет по списку из четырёх значений. Даже если
кого-то удастся уговорить модель ответить не по сценарию, самое рискованное поле для
итогового Excel-отчёта модели не подконтрольно в принципе.

**6. Запись в базу теперь только через сервер.** Раньше анкета писала в
`groups/{code}/responses` напрямую с телефона/ноутбука сотрудника через Firestore REST
с открытым Web API key — работоспособно, но каждый, кто знает формат запроса, мог
отправить произвольные данные напрямую, в обход какой-либо модели. Теперь `interview`
пишет туда сам через Admin SDK, а `firestore.rules` для этой подколлекции ужесточены до
`allow read, write: if false` — прямая запись из браузера закрыта совсем, что бы ни было
в правилах, Admin SDK их не читает, но лишний путь для чужого прямого POST-запроса теперь
не существует и на уровне правил тоже.

**7. Проверил и отклонил.** Формула-инъекция в Excel (классическая уязвимость
CSV-экспорта: ячейка вида `=1+1` от пользователя выполняется как формула при открытии).
Проверил эмпирически: `ExcelJS` пишет обычные строковые значения с типом `t="s"`
(shared string) в OOXML, а не как формулу (`<f>`) — Excel открывает такую ячейку как
текст `"=1+1"`, не вычисляет. Формулы в файле (`functions/lib/xlsx.js`) собираются
кодом только из номеров строк и статичных ссылок на столбцы/листы — данные сотрудников
туда никогда не подставляются как часть формулы. Отдельного исправления не потребовалось.
